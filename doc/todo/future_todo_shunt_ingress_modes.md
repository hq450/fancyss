# fancyss 未来待办：分流入口模式分层草案

本文用于记录 fancyss 后续在 `xray 分流模式` 下，入口引流策略的分层演进方向。

当前先记录概念和边界，不立即实施。

---

## 一、背景

当前 fancyss 在 `xray 分流模式` 下，外层引流和内层分流之间存在一个核心问题：

- 外层负责决定“流量是否进入 xray”
- 内层负责决定“进入 xray 后交给哪条分流规则”

如果外层没有把某类流量送进 xray：

- 那么内层分流规则根本没有机会命中

因此，当前在 `大陆白名单引流` 场景下，需要额外构建一层“分流代理域名集合”：

- 将当前启用分流规则中，目标为代理节点的域名集合并入外层黑名单
- 以保证这些流量一定能进入 xray，再由内层规则继续细分

这套方案是正确的，但也带来两个现实问题：

1. 启动链路变重
2. 用户难以理解“外层引流”和“内层分流”之间的关系

所以后续更合理的方向，不是继续把所有模式都混在一起，而是把入口模式明确分层。

---

## 二、目标

后续将 `xray 分流模式` 下的入口策略，逐步明确为不同语义层级：

1. 全量引流
2. 大陆白名单引流（宽松）
3. 大陆白名单引流（严格）
4. 按需引流

每种模式都应该做到：

- 用户语义明确
- 行为可解释
- 启动成本与目标相匹配

也就是说：

- 追求性能的模式，不强行保证“外层完全覆盖内层”
- 追求完整性的模式，再承担额外运行时准备成本

---

## 三、模式定义

### 1. 全量引流

语义：

- 外层默认将流量全部送入 xray
- 内层分流规则负责最终出口选择

特点：

- 外层不需要额外构建“分流代理域名黑名单”来兜底
- 启动链路相对更简单
- 更适合已经明确希望“全部交给 xray 处理”的用户

当前判断：

- 这类模式下，`shunt_proxy` 相关补偿逻辑后续可以弱化甚至跳过

### 2. 大陆白名单引流（宽松）

语义：

- 继续使用传统“大陆白名单外流量引流”的入口策略
- 不强求外层完整覆盖内层分流规则

特点：

- 启动更轻
- 逻辑更接近当前传统模式
- 允许部分本应命中内层规则的流量，因为外层未引流而漏掉

适合：

- 更在意性能
- 能接受“覆盖不绝对完整”的用户

### 3. 大陆白名单引流（严格）

语义：

- 继续使用大陆白名单作为入口基础
- 但额外将当前启用分流规则中“必须走代理”的域名/IP 尽量反推到外层

特点：

- 尽量保证“外层能覆盖内层”
- 更符合“分流规则一旦配置，就应尽量可靠命中”的直觉
- 启动链路更重

适合：

- 更在意规则完整性
- 能接受更高运行时准备成本的用户

说明：

- 当前 fancyss 的实现方向，实质上更接近这一类

### 4. 按需引流

语义：

- 外层不再做“大面积默认引流”
- 只把用户明确配置的合集 / 规则对应流量引流到 xray

特点：

- 理论上是最干净的长期方案
- 可以显著降低“兜底规则”的存在感
- 外层与内层关系更清晰
- 但实现复杂度最高

适合：

- 未来分流体系成熟后再推进

当前判断：

- 这是长期方向，不是当前阶段优先事项

---

## 四、建议的产品表达

后续前端如果要暴露这些策略，建议不要直接把实现细节暴露给用户，而是用更容易理解的文案：

- `全量引流`
- `大陆白名单（宽松）`
- `大陆白名单（严格）`
- `按需引流`

其中：

- `宽松` 强调“更轻、更快、不保证完全覆盖”
- `严格` 强调“更完整、更稳、启动更重”

---

## 五、建议的实施顺序

### 第一阶段

只做概念分层，不立即改实现。

目标：

- 在文档中先固定术语
- 避免后续讨论时混用“入口模式”“外层引流”“严格/宽松”等口径

### 第二阶段

优先拆出：

- `大陆白名单（宽松）`
- `大陆白名单（严格）`

原因：

- 这两者都基于当前实现演进
- 风险最小
- 也最能直接解决“性能”和“完整性”之间的取舍问题

### 第三阶段

再评估：

- `全量引流` 下是否彻底跳过 `shunt_proxy` 补偿逻辑

### 第四阶段

最后再设计：

- `按需引流`

原因：

- 这会改变当前入口层设计，不适合现在提前重构

---

## 六、当前结论

当前阶段继续保持现状：

- 不立即拆分入口模式实现
- 不立即推进按需引流
- 只把这套模式分层先固定为后续演进目标

这样后续无论是继续优化启动链路，还是调整分流 UI / 术语，都有统一的参考基线。
